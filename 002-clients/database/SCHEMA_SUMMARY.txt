TABLE OVERVIEW
================================================================================

1. CUSTOMERS (Core)
   ├─ Purpose: Central customer information and company details
   ├─ Fields: 40+ (including company info, contact, technical details, tier selection, add-ons)
   ├─ Key Relationships: Parent to all other tables
   ├─ Indexes: 6 (customer_id, email, status, tier, is_active, created_at)
   └─ Business Logic: Tracks complete customer lifecycle from prospect to churned

2. DATABASES
   ├─ Purpose: Track provisioned PostgreSQL databases
   ├─ Fields: 25+ (database details, server info, resource allocation, backup config)
   ├─ Key Relationships: Child of customers (FK: customer_id)
   ├─ Indexes: 5 (customer_id, database_name, hostname, status, health)
   └─ Security: Password hash field (NEVER plaintext!)

3. BILLING
   ├─ Purpose: Track billing cycles and payment status
   ├─ Fields: 20+ (billing cycle, payment method, price breakdown, discounts)
   ├─ Key Relationships: Child of customers (FK: customer_id)
   ├─ Indexes: 4 (customer_id, next_billing_date, payment_status, stripe_customer_id)
   └─ Stripe Integration: stripe_customer_id, stripe_subscription_id

4. INVOICES
   ├─ Purpose: Detailed invoice history with line items
   ├─ Fields: 20+ (invoice details, amount breakdown, payment tracking, Stripe IDs)
   ├─ Key Relationships: Child of customers (FK: customer_id)
   ├─ Indexes: 5 (customer_id, invoice_number, invoice_date, payment_status, due_date)
   └─ Transparency: line_items JSON field shows our_cost vs your_price

5. SUPPORT_TICKETS
   ├─ Purpose: Track customer support requests
   ├─ Fields: 20+ (ticket details, priority, status, SLA tracking)
   ├─ Key Relationships: Child of customers (FK: customer_id)
   ├─ Indexes: 6 (customer_id, ticket_number, status, priority, type, created_at)
   └─ SLA Tracking: Automatic response time calculation and SLA compliance

6. SUPPORT_MESSAGES
   ├─ Purpose: Conversation logs within support tickets
   ├─ Fields: 10+ (sender info, message text, attachments, internal flag)
   ├─ Key Relationships: Child of support_tickets (FK: ticket_id)
   ├─ Indexes: 2 (ticket_id, created_at)
   └─ Features: Internal notes vs customer-visible messages

7. CUSTOMER_WORKFLOW
   ├─ Purpose: Track onboarding and lifecycle workflow status
   ├─ Fields: 35+ (12 workflow checkpoints × 3 fields each + metadata)
   ├─ Key Relationships: Child of customers (FK: customer_id, UNIQUE constraint)
   ├─ Indexes: 3 (customer_id, current_stage, blocked)
   └─ Workflow Stages: 12 checkpoints from form submission to go-live

8. NOTES
   ├─ Purpose: Internal customer notes and communications
   ├─ Fields: 10+ (note type, subject, text, author, flags, follow-up)
   ├─ Key Relationships: Child of customers (FK: customer_id)
   ├─ Indexes: 5 (customer_id, note_type, is_important, follow_up, created_at)
   └─ Features: Follow-up tracking, importance flagging

9. ACTIVITY_LOG
   ├─ Purpose: Complete audit trail of all system actions
   ├─ Fields: 12+ (entity info, action details, before/after states, actor info)
   ├─ Key Relationships: Optional FK to customers (can be NULL for system events)
   ├─ Indexes: 5 (customer_id, entity, action_type, created_at, performed_by)
   └─ Compliance: GDPR/HIPAA audit trail, change tracking

10. SCHEMA_MIGRATIONS
    ├─ Purpose: Track database schema versions
    ├─ Fields: 5 (version, description, applied_at, applied_by)
    ├─ Key Relationships: None (standalone)
    └─ Migration Strategy: Tracks all schema changes for version control

SAMPLE QUERY PATTERNS
================================================================================

1. Active Customers Dashboard
   → SELECT * FROM v_active_customers;

2. Revenue Analysis
   → SELECT * FROM v_customers_by_revenue LIMIT 10;

3. Support Queue
   → SELECT * FROM v_open_support_tickets WHERE priority = 'critical';

4. Onboarding Pipeline
   → SELECT * FROM v_onboarding_pipeline WHERE blocked = 0;

5. Financial Metrics
   → SELECT * FROM v_mrr_summary;

6. Overdue Invoices
   → SELECT * FROM invoices WHERE payment_status = 'overdue' AND due_date < DATE('now');

7. Customer Lifetime Value
   → Complex query joins customers + billing, calculates days_active * monthly_rate

8. Support SLA Compliance
   → Aggregates support_tickets by ticket_type, calculates avg response time and SLA %
